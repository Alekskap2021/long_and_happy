# ТЗ: редизайн сайта «Долго и счастливо»

Документ для дизайна и последующей вёрстки. Опирается на прототип и продуктовую логику из README: воронка «ситуация → понимание → микроопыт → подходящий следующий шаг», а не каталог курсов.

Статус: черновик для согласования  
Стек: TypeScript, Next.js (App Router), React Query, Tailwind CSS, zod  
UI-слой редизайна: Base UI + CSS color variables (см. §5.5–5.6)

---

## 1. Цель и границы

### Цель

Обновить визуальный язык, типографику и UX так, чтобы сайт ощущался спокойным, взрослым и доверительным — и при этом усиливал узнавание ситуации и вёл к бесплатному микроопыту, а не к «купить курс».

### Не цель этого редизайна

- Менять продуктовую логику, таксономию, шаблоны сущностей, API и модель контента
- Подключать оплату, CRM, LMS, личный кабинет
- Делать отдельный уникальный дизайн под каждую тему

### Критерий успеха

За 10–15 секунд на главной пользователь понимает: о чём проект, кому подходит, с чего начать бесплатно. Бренд читается без навигации. Маршрут к диагностике / библиотеке / продукту остаётся ясным.

## 2. Продуктовая рамка (сохранить)

| Принцип | Требование |
| --- | --- |
| Не классический лендинг психологов | Нет схемы «мы психологи → курсы → купить» как главного сценария |
| Воронка | Ситуация → понимание → микроопыт → подходящий следующий шаг |
| Продукты как уровни задачи | Практикум / курс / разговорник / консультация — разные ответы на разные состояния, не равноправный каталог |
| Границы формата | Явно: не замена терапии, не «правильные фразы», не обещание изменить партнёра |
| Безопасность | При признаках небезопасности — маршрут к консультации / профильной помощи, не к курсу |

### Маршруты (не ломать URL)

| Страница | Маршрут |
| --- | --- |
| Главная (блочная) | `/` |
| Библиотека | `/besplatno`, `/besplatno/[slug]` |
| Темы | `/temy`, `/temy/[slug]` |
| Диагностика | `/diagnostika/[slug]` |
| Курсы и практикумы | `/kursy`, `/kursy/[slug]` |
| Консультации | `/konsultacii` |
| О нас | `/o-nas` |
| Служебные | `/oplata`, `/konfidencialnost`, `/obrabotka-dannyh`, `/kontakty` |

Шаблоны сущностей сохранить:

- тематический хаб: сцена → разбор → примеры → диагностика → материалы → следующий шаг → note про терапию
- продукт: ситуация → переопределение → для кого / не для кого → результат → метод → программа → авторы → границы → цена/CTA
- материал: текст → «что дальше» → связи с темой и продуктом

## 3. Аудитория и тон

**Кто приходит.** Люди в близких отношениях с повторяющимися трудными разговорами (деньги, просьбы, границы, после ссоры и т.д.). Часто уже «начитаны», но застревают в сцене.

**Тон.** Спокойный, точный, без эзотерики и мотивационного давления. Голос двух авторов (цель vs действие) должен ощущаться в дизайне, не только в тексте.

**Недопустимо**

- Таймеры, искусственный дефицит, «спасём отношения за N дней»
- Клинический / «медицинский» UI
- Стоковые «счастливые пары» как главный визуальный язык
- Подмена образовательного формата витриной чудесных кейсов

## 4. Что меняем / что не трогаем

### Меняем

- Визуальная система: цвет (CSS variables / modern color space), шрифты, ритм секций, иллюстрации
- Сдержанный motion без переборов (см. §5.5)
- Компонентный слой интерактива на Base UI (см. §5.6)
- Hero и композиция первого экрана
- Навигация и иерархия CTA (диагностика vs библиотека vs продукты)
- Списки и превью библиотеки, тем, продуктов — без «дашбордности»
- Состояния форм, диагностики, waitlist
- Мобильная адаптация и доступность

### Не меняем без отдельного решения

- Информационная архитектура и URL
- Сущности контента и блочная главная (`enabled` / порядок в конфиге)
- Логика диагностики и scoring
- Тексты продуктов и тем как отдельный workstream: дизайн должен выдерживать длинный editorial-текст в текущем объёме

## 5. Визуальное направление

### 5.1. Бренд-тест первого экрана

После удаления навбара первый экран всё ещё должен однозначно быть «Долго и счастливо»: название — hero-уровень, не мелкий логотип. Заголовок не перебивает бренд.

### 5.2. Композиция первого viewport

Один кадр, не дашборд. Обычно только:

1. бренд
2. один заголовок
3. одна короткая поддерживающая фраза
4. одна группа CTA
5. один доминирующий визуальный якорь (полноширинный фон / плоскость; не inset-карточка)

Не выносить в первый экран: статистику, расписание, адрес, «на этой неделе», отзывы, сетку продуктов, промо-чипы и плавающие бейджи поверх hero.

### 5.3. Стиль

- Выбрать **одно** ясное направление (атмосфера разговора / внимания / паузы), не generic «психологический wellness»
- Избегать типичных AI-клише:
  - фиолетовые / indigo-градиенты
  - warm cream + terracotta + serif «как у всех» без собственной идеи
  - газетная сетка с hairline-линейками и плотными колонками
- Текущий прототип (тёплая бумага + terracotta + Inter / Source Serif) — **стартовая точка для пересмотра**, не финал
- Шрифты: выразительные, с кириллицей; не оставлять Inter/system как финальный выбор
- Фон: не плоский single-color; допустимы мягкий градиент, текстура, фото или иллюстративная плоскость
- Иллюстрации: абстрактные, **без лиц и надписей**, в одной палитре; роли `band` / `block` / `thumb` сохранить
- Карточки: по умолчанию нет; в hero запрещены. Карточка допустима только если без рамки / тени / фона ломается взаимодействие (фильтры, выбор ответа в диагностике)
- Одна задача на секцию: один смысл, один заголовок, обычно одна короткая поддерживающая фраза
- Motion — по правилам §5.5, не «анимация ради анимации»

### 5.4. Цветовая система на CSS-переменных

Цвета — не разрозненные hex в компонентах, а единый слой токенов.

**Принципы**

- Все смысловые цвета живут как CSS custom properties и пробрасываются в Tailwind через `@theme` в `src/app/globals.css`
- В компонентах и макетах использовать **семантические** имена (`--color-ink`, `--color-paper`, `--color-accent`, `--color-line`, `--color-danger` / boundaries), а не сырые «orange-600»
- Для палитры предпочтителен современный color space: **OKLCH** (или OKLab) в переменных — удобнее держать одинаковую светлоту/контраст и строить оттенки через `color-mix()`
- Hover / pressed / soft-фоны считать от базового токена (`color-mix`, относительная яркость), а не рисовать отдельный «магический» hex вручную на каждый стейт
- Контраст текста к фону — WCAG AA как минимум; токены проверяются парами (`ink` на `paper`, `paper` на `accent`)
- Отдельный набор для состояний: default / hover / focus / disabled / selected / invalid; focus-кольцо тоже из токенов
- Допускается лёгкая поддержка `color-scheme` / будущей тёмной темы через переопределение тех же переменных — но тёмная тема **не обязательна** в первой волне
- Иллюстрации и UI делят одну палитру: ключи иллюстраций не живут своей «второй радугой»

**Минимальный набор токенов (ориентир)**

| Группа | Примеры |
| --- | --- |
| Поверхности | `paper`, `paper-deep`, `paper-card`, `elevated` |
| Текст | `ink`, `ink-soft`, `ink-muted` |
| Линии | `line`, `line-strong` |
| Акцент | `accent`, `accent-hover`, `accent-soft` |
| Вторичный акцент | `forest` / аналог, `*-soft` |
| Смысловые | `boundaries` / warning soft, без «alarm red» по умолчанию |
| Focus | `ring` / outline |

Дизайн в Figma (или аналоге) должен отдавать те же имена токенов, что уйдут в CSS — без ручного переименования на этапе вёрстки.

### 5.5. Анимация (без переборов)

Motion нужен, чтобы создать присутствие и иерархию, не чтобы украсить каждую секцию.

**Бюджет**

- На весь сайт — **2–3 осмысленных приёма**, повторяемых системно
- Рекомендуемый набор:
  1. спокойное появление hero / ключевых секций при первом заходе
  2. переход между шагами диагностики (смена вопроса, прогресс)
  3. отклик интерактива: кнопка, выбранный ответ, открытие мобильного меню / фильтров
- Длительности короткие: ориентир **180–320ms** для UI, до **400–500ms** только для крупных смен кадра (шаг диагностики)
- Easing спокойный (`ease-out` / стандартный product-easing), без пружин и «jelly»

**Можно**

- Fade + небольшой сдвиг по оси Y (4–12px) при появлении
- Кроссфейд содержимого шага диагностики
- `transition` на цвет / border / opacity у кнопок и выбранных опций
- Один аккуратный scroll-linked или in-view эффект на главной — если не спорит с чтением

**Нельзя**

- Параллакс, бесконечный float, glow-пульсации, конфетти, typewriter в hero
- Анимация каждого заголовка / каждой карточки в списке
- Scroll-jacking, тяжёлые timeline на весь viewport
- Автоплей больших motion-блоков, которые мешают читать длинный текст
- Разные «фирменные» анимации на каждой странице

**Доступность и техника**

- Обязательно уважать `prefers-reduced-motion: reduce`: оставляем мгновенную смену состояния или короткий fade без смещения
- Анимация не блокирует ввод и не задерживает LCP
- Предпочтительно CSS transitions / `@starting-style` / View Transitions API для смены шага; тяжёлые JS-timeline библиотеки — только если без них нельзя обойтись
- Для Base UI-компонентов анимировать через CSS на data-атрибутах открытого/закрытого состояния, а не через произвольный JS-хаос

**Спека motion (обязательный deliverable)**

Для каждого из 2–3 приёмов зафиксировать: триггер, свойство, длительность, easing, reduced-motion fallback.

### 5.6. Компоненты: Base UI + токены

Интерактивный UI собираем на **Base UI** (headless-примитивы с доступностью из коробки): меню, диалоги, disclosure, focus management, формы там, где нужны сложные паттерны. Визуал — наш, через CSS-переменные и тонкие обёртки в `src/components/ui/*`.

**Зачем**

- Доступность (клавиатура, focus trap, aria) не изобретаем заново
- Стили полностью контролируем токенами — без чужого look-and-feel
- Одинаковые стейты open/close удобно стыковать со сдержанной CSS-анимацией

**Правила слоя**

- Base UI = поведение; внешний вид только через наши классы / переменные
- Не тащить готовую «красивую» тему стороннего kit поверх бренда
- Кнопки, ссылки, поля, alert/boundaries, теги форматов — единый UI-kit на токенах
- Сложные паттерны первой волны-кандидаты на Base UI: мобильное меню, фильтры библиотеки, disclosure «программа курса» (если останется), диалог подтверждения заявки, focus-состояния опций диагностики
- Простые статичные секции и editorial-текст — обычная вёрстка, без обёртки в примитивы «на всякий случай»
- Публичный API обёрток стабильный (`Button`, `ButtonLink`, `Field`, …): страницы не импортируют Base UI напрямую без нужды

**Связка с цветом**

- Варианты компонента (`primary` / `secondary` / `ghost` / `inverse`) читают семантические CSS-переменные
- Смена палитры при редизайне = правка токенов, а не охота по классам в десятках файлов
- Состояния `hover` / `focus-visible` / `disabled` / `aria-invalid` описываются в одном месте

**Что не делаем**

- Не смешиваем несколько headless-библиотек (Base UI + Radix + Headless UI) без причины
- Не копируем dashboard-паттерны Base UI demos на маркетинческие страницы
- Не заменяем контентную модель сайта «компонентным конструктором» из карточек

## 6. Страницы и UX-требования

### Главная `/`

Состав блоков уже задан конфигом: hero → situations → diagnostic → method → levels → library → authors (+ `boundaries` по флагу).

Требования к редизайну:

- визуальная иерархия и ритм чтения
- situations — узнавание сцены, не витрина
- levels — состояния человека, не прайс-лист
- authors — «два слышания», не CV

### Библиотека `/besplatno` и материал `/besplatno/[slug]`

- фильтры читаемы на мобиле
- длинный текст — комфортный editorial-ритм
- блок «что дальше» всегда виден после контента

### Тема `/temy/[slug]`

- сцена — эмоциональный якорь, не декоративный диалог в рамке
- порядок секций шаблона сохранить
- therapy note не прятать в подвал страницы

### Продукт `/kursy/[slug]`

- сохранить структуру шаблона
- блоки «не для кого» и «границы» не прятать в аккордеон мелким шрифтом
- CTA соответствует `availability` (waitlist / checkout / contact / soon)

### Диагностика `/diagnostika/[slug]`

- пошагово, спокойно, без геймификации и «результата личности»
- результат с понятными next steps
- unsafe-ветка — приоритет консультации
- UI не обещает историю ответов / кабинет (ответы не сохраняются)

### Консультации, о нас, юридические

- тот же визуальный язык
- этика и дисклеймеры — первоклассный контент, не afterthought в футере

## 7. Навигация и CTA

| Приоритет | Действие |
| --- | --- |
| Primary | Пройти диагностику (или эквивалент микроопыта) |
| Secondary | Начать бесплатно / выбрать ситуацию |
| Tertiary | Продукты и консультации как следствие маршрута |

На мобиле: доступ к диагностике и библиотеке не больше чем в 2 тапа с любой ключевой страницы.

Текущая навигация-ориентир:

- Начать бесплатно
- Темы
- Курсы и практикумы
- Консультации
- О нас
- CTA: Пройти диагностику

---

## 8. Контент и этика (для дизайна)

- Не маскировать образовательный формат под клинику
- Дисклеймеры и границы заметны, но без лишнего «medical red alert»
- Отзывы (когда появятся) — без «до/после» и чудо-кейсов
- Диагностика не выглядит как клинический тест или типология личности
- Перед продом снять `noindex` отдельным решением; в макетах заложить нормальные title / OG-превью

## 9. Технические ограничения

| Параметр | Значение |
| --- | --- |
| Стек | Next.js App Router, React, Tailwind CSS v4, React Query, zod |
| UI-примитивы | Base UI для интерактива; визуал на наших токенах в `src/components/ui` |
| Цвет | CSS custom properties (+ OKLCH / `color-mix` по возможности); семантика, не сырые hex в JSX |
| Motion | CSS-first, бюджет 2–3 приёма; обязательный `prefers-reduced-motion` |
| Контент | Через `src/content/repository.ts` и схемы; дизайн не завязывать на хардкод страниц |
| Главная | Блоки из `src/content/data/home.ts`; порядок и `enabled` не ломать |
| Адаптив | Mobile-first; ключевые сценарии на 360–430px и desktop |
| A11y | Контраст WCAG AA, `focus-visible`, клавиатура для диагностики и форм |
| Производительность | Hero без тяжёлых LCP-сюрпризов; шрифты с `display: swap`; анимация не ухудшает INP/LCP |
| Аналитика | Сохранить точки воронки `TrackFunnelStep` |

## 11. Deliverables

1. Moodboard: 1–2 направления + выбранное финальное
2. UI-kit: кнопки, ссылки, поля, меню/фильтры, alert/boundaries, роли иллюстраций
3. Цветовые токены: таблица семантических CSS-переменных (желательно OKLCH) + пары контраста
4. Макеты desktop + mobile по приоритету из §10
5. Спека motion на 2–3 приёма: триггер, свойства, ms, easing, reduced-motion
6. Список компонентов на Base UI vs чистая вёрстка
7. Redline / имена токенов 1:1 с будущим `globals.css`
8. Короткий design QA checklist

## 12. Критерии приёмки

- [ ] Бренд-тест первого экрана пройден
- [ ] Первый viewport без вторичного маркетингового шума
- [ ] Воронка читается без объяснений
- [ ] Длинные тексты темы / материала / продукта читаются без усталости
- [ ] «Не для кого» и границы формата заметны
- [ ] Диагностика удобна на мобиле end-to-end
- [ ] Нет клише «фиолетовый wellness» / шаблонного cream+terracotta / газетной сетки — либо это осознанный и согласованный выбор
- [ ] Все страницы первой волны покрыты макетами
- [ ] Цвета заданы семантическими CSS-переменными; в компонентах нет разрозненных «сырых» hex
- [ ] Motion в бюджете 2–3 приёмов, без параллакса/glow/анимации каждой карточки; есть reduced-motion
- [ ] Интерактивные паттерны опираются на Base UI (или явно помечены как исключение)
- [ ] Токены и компоненты стыкуются с текущей архитектурой без переписывания IA

## 13. Открытые вопросы

1. Объём: только визуальный редизайн UI или ещё пересборка структуры главной / копирайт?
2. Визуальный якорь: иллюстрации как сейчас, фото или смешанный язык?
3. Насколько далеко от текущего look: эволюция или смена направления?
4. Референсы: 2–3 сайта «как нам по тону» и «как не надо»?
5. Формат работы: Figma → потом код, или дизайн сразу в репозитории?
